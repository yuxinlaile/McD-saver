## 一、项目定位

### 1.1 三版定位语（按场景取用）

| 场景 | 文案 |
|---|---|
| 一句话（12 字） | 下单前，先算一遍再点。 |
| 电梯版（40 字） | 麦麦省钱助手：基于麦当劳中国官方 MCP 的点餐省钱 Agent Skill，把券、团购、积分放在同一张桌子上算终局。 |
| 完整版（100 字） | 它不替你下单，只在下单前强制跑一遍省钱检查：领完可领的券、选出当前订单最优券、用官方 `calculate-price` 做无券/带券双价对比、评估积分是否更划算、把临期券的沉默成本算清楚，最后给出「原价 / 优惠 / 实付 / 节省比例」。官方券、美团抖音团购、积分商城四本账同口径对比。 |

**对外只说一句**：*让 AI 帮你用最少的钱吃麦当劳。*（README 首屏已用此句）

### 1.2 差异化坐标

| 对比对象 | 他们通常做什么 | 我们的差别 |
|---|---|---|
| 比价插件 / 优惠券聚合 | 只在一个渠道内找最低价 | 官方券 + 团购 + 积分**四渠道同口径**，算「终局建议」 |
| 通用 MCP 工具集 | 提供能力，不做决策 | 有**方法论**：省钱四步检查、凑单陷阱、券排期、沉默成本 |
| 记账 / 返利类 App | 事后统计 | **事前拦截**：下单前拦截一次，避免"为用券而多买" |
| 其他 Agent Skill | 单一 prompt 包装 | 243 项测试、21 个版本、真实运行留档，**可复现** |

### 1.3 定位红线（写进所有对外内容）

- **非官方**：社区开源项目，与麦当劳公司无隶属/合作/背书关系，商标归权利人；
- **不承诺金额**：「本次可省 ¥X」只来自官方工具实际返回值，不做收益承诺；
- **不自动化下单**：创建订单需用户明确确认，支付始终在官方页面完成；
- **不鼓励囤券**：工具会主动提示"用不完的券是沉默成本"。

### 4.3 可复制文案

**① 知乎回答（问题：「麦当劳怎么点最省钱？」「有哪些好用的 AI Agent 工具？」）**

> 起因很简单：我每周吃两三次麦当劳，券越攒越多，但经常出现"为了用券多买一份"的情况，算下来反而更贵。
>
> 于是我写了个工具，在下单前跑一遍检查：
> 1. 领完可领的券，再用官方 `calculate-price` 做无券/带券双价对比；
> 2. 把美团/抖音团购券按同口径折算进来，给"终局建议"；
> 3. 用券排程算临期券的沉默成本——名义 ¥150 的券包，可能只有 ¥60 用得上。
>
> 举个真实跑出来的例子（麦辣鸡腿堡三件套）：单点 ¥33.50，官方「满 30 减 6」后 ¥27.50，
> 美团「满 40 减 14」团购券同内容折算约 ¥21.69。
>
> 三种用法：Agent Skill（SKILL.md 丢进 Claude Code / Cursor 即用）、独立 CLI（纯标准库，无依赖）、免登录网页试算。
>
> 仓库：https://github.com/yuxinlaile/McD-saver
> 试算页：https://yuxinlaile.github.io/McD-saver/demo.html
>
> 顺带说：不是官方项目，不替你下单，也不保证省多少——所有数字都来自官方接口返回值。欢迎拍砖，尤其是券规则和营养约束这两块。

**② 即刻 / 微博**

> 把「麦当劳怎么点最便宜」做成了一个能算的东西 🍟
>
> 不是比价插件，是下单前的一次强制检查：先领券 → 再选券 → 无券/带券双价对比 → 积分值不值 → 临期券会不会过期。
> 最反直觉的一条：**凑单用券经常更贵**。
>
> 免登录试算（手机可用）：https://yuxinlaile.github.io/McD-saver/demo.html
> 开源仓库：https://github.com/yuxinlaile/McD-saver

**③ 技术向（掘金/X 通用开头）**

> MCP 的 Streamable HTTP 有个坑：服务端可能返回 `text/event-stream`，也可能直接返回 JSON，还可能在 SSE 里夹一条 JSON-RPC error。
> 我一开始把 error 当成"无结果"抛了异常，导致所有工具错误都丢了错误码。
> 这篇写清楚我怎么修的，以及另外 5 个真实踩坑。

### 5.3 投入预算

- 单人，冲刺期日均 **60–90 分钟**，赛后日均 30 分钟；
- 零现金投入（不投放、不买量）；
- 物料一次做，复用 4 周。

## 六、效果衡量

### 6.1 指标分层

| 层级 | 指标 | 数据源 | 取数方式 |
|---|---|---|---|
| 曝光 | 各平台阅读/播放量 | 平台后台 | 手动记录 |
| 访问 | GitHub UV / 试算页 PV | GitHub Traffic | `gh api repos/yuxinlaile/McD-saver/traffic/views` |
| 来源 | 各渠道引荐 UV | GitHub Referrers | `.../traffic/popular/referrers` |
| 转化 | Star / 访问 UV | 计算 | 目标 ≥ 8% |
| 激活 | 试算完成、Release 下载、clone | Release API / Traffic | `.../releases`、`.../traffic/clones` |
| 留存 | 7 日回访、二次 Issue | 人工观察 | 每周抽样 |
| 社区 | Issue / Discussion / PR 数、首次响应时长 | GitHub | `gh issue list` |
| 质量 | **有效 Star 比例** | 抽样 20 个 stargazers | `gh api users/<login>` 看 `created_at` / `public_repos` |

**有效 Star 定义**：账号注册 ≥ 90 天，且至少有一个公开仓库或持续活动记录，且非同一时段批量出现。低于 80% 就要检查来源是否被污染。

### 6.2 基线 vs 目标

| 指标 | 基线（10-19） | 冲刺目标（10-26） | 30 天目标（11-19） |
|---|---|---|---|
| Star | 11 | 28（保守）/ **40（基准）** / 60（进取） | 80–120 |
| 14 天 UV | 51 | 400+ | 1200+ |
| 外部引荐渠道 | 0 | ≥ 4 个域名 | ≥ 8 个 |
| Release 单版下载 | 1–3 | 15+ | 40+ |
| Issue / Discussion | 0 | 8+ | 25+ |
| 有效 Star 比例 | — | ≥ 85% | ≥ 85% |

> 目标按"曝光 → 访问 → 转化"倒推：40 Star 需要约 500 UV，按 3 篇主贴 + 2 个长尾渠道的常态量级是可达而非激进的。

### 6.3 每日 5 分钟看板

```bash
# 今日 Star / Fork
gh api repos/yuxinlaile/McD-saver --jq '{stars:.stargazers_count, forks:.forks_count}'

# 近 7 天访问与来源
gh api repos/yuxinlaile/McD-saver/traffic/views --jq '{uv:.uniques, pv:.count}'
gh api repos/yuxinlaile/McD-saver/traffic/popular/referrers --jq '.[] | "\(.referrer)\t\(.uniques)"'

# 版本下载量
gh api repos/yuxinlaile/McD-saver/releases --paginate \
  --jq '.[] | "\(.tag_name)\t\([.assets[].download_count] | add // 0)"' | head -5

# 新增 Star 的时间分布（判断是否异常集中）
gh api repos/yuxinlaile/McD-saver/stargazers \
  -H "Accept: application/vnd.github.star+json" --jq '[.[] | .starred_at] | .[-10:]'
```

**归因方法**：GitHub Referrers 只给到域名级别，但足够区分 知乎 / 掘金 / 小红书 / 站内。若需要页级数据，可后续自托管 GoatCounter（开源、无 Cookie）；**默认不引入第三方追踪**，避免隐私与合规负担。

### 6.4 复盘节奏

- **每日**：看板 5 分钟，只记录不评价；
- **每周日**：填一张「渠道 → 曝光 → UV → Star」表，砍掉连续两周零转化的渠道；
- **定榜后**：写一篇复盘，公开真实数字（包括没做起来的部分）。

## 七、合规：如何正确地邀请 Star

### 7.1 依据

- **GitHub 社区准则 / 可接受使用政策**：禁止虚假互动、批量注册、自动化刷量；判定后可能限制账号或清除 Star；
- **赛事规则**：排名以 Star 计，明确禁止刷星、多账号、机器人等操纵行为，违者取消资格；
- **常识**：评审能看到的不仅是数字，还有 Star 的时间分布与账号质量——异常增长本身就是负资产。

### 7.2 什么算刷星（一律不做）

| 行为 | 为什么不行 |
|---|---|
| 自己注册多个账号点 Star | 典型刷量，账号关联可查 |
| 互星群 / star-for-star | 非真实兴趣，且形成可识别的时间簇 |
| 买 Star / 买曝光 | 直接违规，且来源账号多为批量号 |
| 抽奖、返现、礼品换 Star | 利益交换，属于操纵排名 |
| 机器人 / 脚本批量点 Star | 违反 API 与自动化政策 |
| 亲友团集中批量点 | 即使真人，也属于"非真实使用者的集中互动"，风险高 |
| 在无关群/私信群发链接 | 骚扰 + 低质量流量 |

### 7.3 合规邀请的五种写法

原则：**先给价值，再提请求；说明背景，允许拒绝；只问一次，不追问。**

1. **内容结尾（最常用）**
   > 如果这个工具帮你少花了一次冤枉钱，欢迎点个 Star；用不上也完全没关系。

2. **说明参赛背景（诚实披露）**
   > 这个项目在参加麦当劳中国开发者创新挑战赛，Star 会计入排名。但更希望你先试用再决定——试算页免登录，30 秒能跑完一单。

3. **对提建议的人（反馈换改进，不换 Star）**
   > 感谢反馈，这条已记进 v2.2.0。如果后面用着顺手，欢迎 Star 让更多人看到；不点也完全不影响我们继续改。

4. **对同赛道开发者（同行交流）**
   > 你们在券规则上的处理比我们细，学到了。我们的实现也放在仓库里，互相参考没问题——不用 Star，能指出问题更有价值。

5. **线下/群聊（一对一，非群发）**
   > 我做了个麦当劳省钱的工具，你要是有兴趣可以试试，链接在这。不用特意去点 Star，用得上再说。

### 7.4 事实性原则

- 所有"省了多少"必须来自官方接口返回值，附截图与订单条件；
- 不使用「最便宜」「保证省钱」「100% 准确」等绝对化表述；
- 明确标注非官方、个人非商业用途、仅限中国大陆；
- 不虚构用户证言，不伪造使用量。

### 7.5 异常自查与补救

| 现象 | 处理 |
|---|---|
| 单日 Star 增量 > 平时 5 倍且来源不明 | 暂停当日所有外发，检查是否被搬运到刷量渠道 |
| Star 账号集中注册于近期 | 抽样 20 个，若有效率 < 70%，在 #275 主动说明并请主办方核验 |
| 被质疑刷星 | 公开 Star 时间分布 + 各渠道帖子链接 + 邀请话术，用证据回应，不争吵 |
| 发现他人搬运/刷量 | 不参与、不转发，必要时向平台举报 |

**底线**：宁可少 20 个 Star，也不要一个说不清来源的 Star。

## 八、风险与预案

| 风险 | 触发场景 | 预案 |
|---|---|---|
| 商标/官方关系误读 | 被当作麦当劳官方产品 | 所有内容首段或末段标注"非官方"，README 免责声明已在 |
| 价格数据时效 | 用户按旧价格预期到店发现不符 | 文案统一写"以官方接口实时返回为准" |
| Token 安全质疑 | 用户担心粘贴 Token | 强调仅本地内存使用、不上传；`--token-file` + 权限检查已有 |
| 平台判定广告 | 知乎/掘金被折叠或限流 | 正文先给完整价值，链接后置；被折叠则改写成纯技术复盘再发 |
| 内容无人看 | 首帖零互动 | 不重复发；换选题（技术向通常比省钱向更稳），一周后再评估 |
| 维护者精力不足 | 评论/Issue 积压 | 设固定响应时段（每天 20:00–20:30），公开说明响应节奏 |
